# Official tunnel-client compatibility

## Meaning

This document defines TunnelTend's local compatibility boundary and its independent retained public evidence. Local verified staging remains installation authority. Native GitHub run/artifact metadata feeds the one accepted-main website publisher; missing central evidence does not disable local updates or unrelated site delivery. Source implementation, activated workflows and actual binary/provider encounters are separate evidence.

TunnelTend depends on the official client's stable release assets and these command families:

- `--version`
- `runtimes list --json`
- `runtimes status <alias> --json`
- `runtimes connect ... --json`
- `runtimes stop <alias> --json`

The adapter normalizes upstream fields before the rest of the application sees them. Unknown or missing structured targets are refused during import.

`client status` performs live help-based capability checks. A new binary is not accepted after update until those checks pass. The Windows release checklist verifies concrete JSON fields and exit codes against the selected release.

## Local installation authority

Maintenance resolves the latest stable release directly from `openai/tunnel-client`. It selects the host architecture, requires a published digest/checksum, guards archive extraction and executable selection, and checks the staged version against the selected release before downtime. The coordinator pins that selected tag for acquisition rather than independently resolving a newer latest release midway through staging. Installed capability/fleet failure retains transactional rollback and explicit incomplete-recovery reporting. No central report, allowlist or website availability is consulted.

Automatic same-version maintenance keeps installed bytes, including when upstream republishes that tag with a different digest. The central reader preserves the old/new official identity for maintainer judgment; a changed digest alone is not a compromise verdict. New installations use the current official asset and checksum. A deliberately forced reinstall remains explicit and cannot bypass checks or permit downgrade. A genuinely newer compatible release resumes ordinary maintenance.

## Maintained upstream context

`docs/research/openai-tunnel-client-release.json` remains an optional dated generated release coordinate, refreshed explicitly with `scripts/Update-UpstreamSnapshot.ps1`. It is not an allowlist or local installation prerequisite. The watch no longer fails because that tracked snapshot changed. `docs/research/openai-tunnel-client-current.md` preserves useful authored semantic context and historical evidence; neither file is a permanent latest-version claim or installation gate. Actual upstream contract failure earns focused adapter work and, when needed, a separately authorized TunnelTend patch.

## Retained qualification and public facts

The qualification producer owns `schemas/client-qualification.schema.json` and `scripts/lib/client-qualification.mjs`. It reports separately on the released TunnelTend package and current source: exact package/build, official release and architecture/asset/digest, actual adapter, updater and harness identity, timestamps, and distribution, credential-free CLI, owned-fleet and connected-consumer boundaries. `passed`, `failed`, `not exercised` and `unavailable` remain distinct. A current-source result is not evidence that a repair exists in the public package. ARM64 acquisition is not ARM64 execution; no active fleet or connected session is `not exercised`.

Qualification schema/contract v2 requires nullable `source.updaterSha256` beside `adapterSha256`; both name bytes from the extracted tested package and must be present for any distribution pass. Its isolated package updater supplies official release selection, architecture selection, download, digest verification, guarded extraction and executable selection. Current-source helpers bootstrap the product package and instrument/report tests; they cannot supply an official acquisition pass for an older released updater. A package without an explicit architecture selector exercises only its native selection route. The other architecture remains `not exercised`, without downgrading supported capability or failing the successfully exercised native route. With no execution, `version-agreement` and `installation-agreement` must each be exactly `not exercised`; only the first five distribution checks can establish archive-only success. Native distribution still requires all seven checks. Fleet and connected-consumer use remain unexercised. The v2 consumer rejects older v1 reports, whose acquisition proof was source-assisted; it does not relabel historical passes as package-owned proof. Official identity-history metadata has its own version and is unaffected by this report revision.

Packages such as 1.0.1 have no `-LibraryOnly` entry. Qualification runs their unmodified updater script in a hidden credential-free child process, with the package-generated configuration pointing only at a new disposable installation and state directory and requiring a published checksum. A successful exit alone is insufficient: the harness reads the package's durable updater receipt, binds its release/asset/digest, checks the selected release metadata, then exercises the package adapter against the actual installed bytes. Foreign-architecture acquisition stays unexercised. No installed user product, Scheduled Task or active fleet participates.

The native artifacts are `client-qualification-release` and `client-qualification-source`, each containing exactly `report.json`. The clean website runner uses `tools/compatibility/github-evidence.mjs` to retrieve retained metadata through the read-only Actions API. It verifies same-repository/default-main workflow, run/attempt/source identity, provider artifact digest and actual expiry, a single bounded regular JSON ZIP entry, and the producer's shared fixed-schema validator. It writes no downloaded paths and executes no artifact content. It rejects PR/fork/other-workflow artifacts, invalid schema, stale report/run identities, expired artifacts, links, traversal, extra files, encryption, CRC/digest mismatch and oversized input. Only schema-checked metadata reaches the Astro templates, which escape text and construct evidence links from native numeric IDs.

Reruns may retain multiple same-name artifacts. Resolve the report's exact native attempt and its package qualification job, including job outcome and upload timing. A successful source job from attempt 1 remains valid if only the release job reruns in attempt 2; the whole first attempt may have failed because of that other job. Keep job outcome distinct from attempt outcome, preserve failed reports, and order observations by provider/check timestamps. Neither artifact-ID rank, name-only downloads nor a blanket latest-attempt requirement selects the correct evidence.

`website/scripts/resolve-compatibility.mjs` assembles build-local `website/artifacts/compatibility/facts.json`. It lists only the three named metadata artifact families, up to ten pages of 100 artifacts per family, and reads every valid retained snapshot and report in that collection. The model merges all received identities before selecting routine qualifications; a newest incomplete snapshot is never baseline authority. Missing/expired/invalid/inaccessible evidence is disclosed; provider outages do not stop ordinary website builds. Incomplete provider/history retrieval or a collection limit suppresses the new history upload, preserving older recoverable snapshots rather than replacing them with partial state. A failed qualification retains its report for diagnosis and cannot overwrite an earlier routine-qualified asset. The public display separates newest observations from last routine-qualified evidence and displays package identity, exact outcomes, checked/observed times, age, run/artifact links and expiry. At 48 hours, age becomes stale disclosure only. On visits, back/forward restoration and return to the page, expired evidence makes all four compact outcomes and routine-qualified availability explicitly unavailable; exact historical outcomes remain in details. Without JavaScript the actual times and the age **at build** remain explicit. No central result, freshness threshold or website state gates local installation.

## Identity history and expiry

The same official tag/architecture with different bytes is exceptional. Existing same-version installations retain their bytes; a repeat observation, reversion, changed TunnelTend package or changed qualification contract cannot silently close a known mutation. The existing clean Website controller retains `client-qualification-history`, also one `report.json`, carrying only the currently observed baseline plus open identity changes, original first-observation run/artifact coordinates and timestamps. This is native metadata in the selected artifact home, not a package-version registry, Git writer, cache service or second publisher. Multiple retained snapshots are merged so a later incomplete snapshot cannot erase a known open change. Old routine tags are not accumulated as a permanent registry.

History uses its own exact fixed-shape validation and requires a same-repository/default-main Website run plus an actual built-source commit in accepted-main ancestry. A queued event's SHA is not substituted for the source actually built. History preserves identities only: it never renews qualification time, copies a pass past the original artifact's expiry, or fabricates an earlier baseline when prior history is unavailable. A lost baseline with only changed-byte repeats must remain unknown. Meaningful open incidents belong in ordinary maintainer Work before temporary evidence expires.

History schema 2 carries explicit `continuity`: `retained` or `unknown`. Missing/expired history bootstraps as unknown, and that marker survives saved/read-back snapshots, repeated reports, digest reversion and tested-package changes. Legacy schema 1 identities are retained with unknown continuity. The retained `continuousSince` boundary permits dated routine qualification for genuinely newer releases published after continuous observation began, without clearing unknown prehistory or open same-tag changes. Repeats or reversions of a pre-boundary tag cannot manufacture a routine-qualified baseline; partial retrieval cannot supply one either. Current reports still show their actual separate boundary outcomes. Neither a current pass nor merely finding a saved snapshot upgrades unknown continuity. No manual baseline/reset ritual is required for future releases.

All three metadata artifacts request 90 days; the current repository readback was 90 days with a 90-day maximum. No repository setting is changed. Consumers use actual provider `expires_at`; retention of 48 hours or less is disclosed. GitHub may omit already-expired artifacts entirely, so an empty lookup is honestly `missing-or-expired`. A provider outage is not a false clean history. Recovery is the next successful ordinary qualification/controller build using remaining valid native reports and snapshots. Complete loss of that native history is explicitly unavailable, not reconstructable from a green current probe. No separate backup service is promised.

## One production controller and failure encounter

`.github/workflows/website.yml` remains the only credentialed publisher and uses its existing production concurrency group. Relevant accepted-main pushes, manual production dispatch and a successful filtered `Upstream compatibility watch` completion enter that controller. Executable qualification and publication use separate disposable runners. The publisher checks out **current main after acquiring the concurrency slot**, not the older qualification/event SHA, then resolves current retained evidence. A failed qualification cannot block independent website delivery. Metadata/build failure leaves the deployed site in place; a later valid build can recover without per-release source edits.

The executable job receives no deployment/legal credentials, OIDC, write token, reusable cache or persisted checkout credential. Website retrieval uses only Actions/contents read permissions. The existing legal projection remains in the publication build; the Cloudflare credential remains solely in the existing deploy step. No second mutation identity or credential is introduced. The generated display and job summary identify the website commit and consumed evidence run/artifact identities; actual public acceptance must read both from the deployed output.

Compatibility failures remain failed provider runs. The existing GitHub Actions per-run notification route for `Wolfsblvt` and ordinary maintainer CI stewardship carry failure encounter; a run failure alone is not notification delivery or stopped-agent wake. A prior actual watch-failure notification establishes the existing receiver route, while activation of a changed producer still needs its actual failure/report/receiver encounter. Katja owns that activation/readback and triage. Group failures by release tag, digest, architecture, contract and failed check IDs; record recovery against the same identity. Do not manufacture green to silence alerts or add a speculative deduplication bot.

## Focused verification

From the repository root, use Node 24:

```powershell
node --test tools/compatibility/*.test.mjs
```

From `website/`, `node scripts/resolve-compatibility.mjs` reads public metadata (or uses `GH_TOKEN` with Actions read). `npm test` includes trust/state tests, existing site checks and the built-output contract. Tests and local rendering prove their own boundaries; actual native artifact download/expiry, failure delivery, current-main publication and public readback remain explicit hosted/activation evidence. A future naturally published upstream release is later field confirmation, not a calendar gate on source implementation.
